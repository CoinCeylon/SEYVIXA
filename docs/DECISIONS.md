## 2026-11-24 — Open items resolved (decided by Abdul)

| # | Decision | Reason |
|---|---|---|
| D15 | `actions.status` gains `PENDING_APPROVAL`. Evaluate returns `APPROVAL_REQUIRED` and sets `PENDING_APPROVAL`; a verified approval moves the action to `APPROVED`. An `ALLOW` that needs no approval goes straight to `APPROVED`. A `DENY` creates no action record (only a `policy_events` row). | Section 8 had no status for an evaluated action waiting for approval. |
| D16 | Policy version is one configuration constant `POLICY_VERSION`, bumped by hand when policy logic changes. It is stored on the action as `actions.policy_version` (additive column). Execute compares it with the current value; a mismatch gives `POLICY_VERSION_STALE`. Revoked grants are already caught by revalidation. | The Blueprint binds a ticket to a policy version but gave no source for it. |
| D17 | Action types and approval. `SUPPLIER_SEARCH`, `QUOTE_READ`, `FILE_READ`, `PROPOSE_PURCHASE` are `ALLOW` or `DENY` by grant. `ESCROW_LOCK` needs `APPROVAL_REQUIRED` (message approval). `ESCROW_RELEASE` and `ESCROW_REFUND` need `APPROVAL_REQUIRED`, where the owner's transaction signature is the approval, checked at execute. `BUDGET_RESERVE` is not an action type (it uses the direct route from D2). | The Blueprint did not say which actions need approval. |
| D18 | `getTxStatus`: found = the chain-data API returns the transaction in a block; confirmed = found with at least `CONFIRMATION_DEPTH` block confirmations. Default `CONFIRMATION_DEPTH` = 3, in config, labelled a prototype setting. Anything else is `not_found`. | "found" and "confirmed" were undefined. |
| D19 | T2.1 (owner session) moves from 30 Nov to 27 Nov so it lands before T1.1b and T1.6 (28 Nov). Until then the cards may use one stub `getSessionOwnerId(req)`. T2.1 replaces it behind the same signature. Remove the stub before 5 Dec. | Routes due 28 Nov needed the session. |
| D20 | Seed command is `pnpm seed` (guide changed from `npm run seed`). | The repo uses pnpm (D12). |
| D21 | Reason code `GRANT_INTEGRITY_FAILED` is added to D4. It is used for a tampered grant instead of `GRANT_MISSING`. | A tampered grant needs its own code. |
| D22 | Approved as proposed: T8.6 target 8 Dec; paths `docs/procurement-agent-prompt-template.md`, `apps/web/lib/wallet/`, `docs/evidence/interview-log.md`; T0.3b depends only on T0.3a; T5.7 also records the Cardano level. | Open items from the prompt pack. |
| D23 | The interview log is anonymised: role and business type only, no names, phone numbers or business names, because the repo is public. Quotes need permission. | Privacy of interviewees. |
