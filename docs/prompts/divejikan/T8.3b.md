## Why this card exists

A fresh-session security review of the merged T8.3 verifier found 4 blockers. In plain words:

1. The verifier checks the owner's approval with a public key taken from inside the receipt itself. Anyone could forge an approval with a throwaway key and still get VERIFIED. The Blueprint forbids this (Section 9 item 12: never trust keys supplied inside the evidence).
2. The approval format in the verifier (`<pubkey>:<sig>` over canonical JSON) is invented. The Blueprint says the owner signs with a Cardano wallet (CIP-30 `signData`, CIP-8), which gives a COSE_Sign1 signature and a COSE_Key. A real wallet signature would always be REJECTED today.
3. The verifier reads required signers from a field called `hash`. The review says the Blockfrost API calls it `witness_hash`. If that is right, every real release or refund is REJECTED. Tests never caught it because the chain data is mocked.
4. The verifier counts reference inputs and collateral inputs as "spends the escrow UTxO". A transaction that only references the escrow output would pass the "release spends the escrow" check.

The same review also found that 19 of 30 deliberate code breaks (mutations) were not caught by any test. This card fixes the blockers and closes those test gaps.

### Section 6.5 (Owner signature)

~~~~markdown
The owner signs the message `{domain: "seyvixa-approval-v1", action_hash, nonce, expires_at}` with the wallet registered for the owner (CIP-30 `signData`, CIP-8 message signing). The server verifies it in `POST /api/approvals`.
~~~~

### Section 6.5 (Signature verification, at registration and at every approval)

~~~~markdown
Use a maintained helper if the pinned toolchain has one (for example in the Mesh SDK) and test it with a real wallet signature. Otherwise implement these checks:

1.  Decode the COSE_Sign1 and COSE_Key. The algorithm must be EdDSA (Ed25519). Take the 32-byte public key from the COSE_Key.
2.  Check that the address in the COSE_Sign1 protected header equals the registered address (at registration, the address the owner selected).
3.  Check that the payload bytes equal the expected message exactly: the challenge, or the approval message the server builds from the stored action.
4.  Verify the Ed25519 signature over the COSE `Sig_structure` (context `Signature1`, the protected header, empty external data and the payload).
5.  Derive the payment key hash as the Blake2b-224 hash of the public key, and check that it equals the payment credential inside the address. At approval time, also check that it equals the stored `payment_key_hash`.
6.  Check that the nonce is unused and unexpired, then mark it used atomically.

Never use a key, address or key hash supplied in the request.
~~~~

### Section 6.8 (Verification, steps 2 and 5, result)

~~~~markdown
2. Verify the owner's approval signature over {domain, action_hash, nonce, expires_at}. Confirm that owner_key_hash equals the buyer key hash in the on-chain datum (or report the "approval key not bound to escrow buyer key (fallback)" label). In the full view, also recompute action_hash from approved_action.
5. Settlement.
   - released: confirm release_tx_id is confirmed on the expected network, that one of its inputs is exactly escrow_utxo_ref, that an output pays at least the locked amount to the supplier key hash from the datum, and that the buyer key hash is among its required signers.
   - refunded: the same checks with refund_tx_id, an output paying the buyer key hash, and a validity range that starts after the refund deadline.
   - locked: there is no settlement transaction. Report "locked, not settled" and make no release claim.

The result is VERIFIED, REJECTED (any check fails) or UNVERIFIABLE (a chain API could not be reached). UNVERIFIABLE is never reported as VERIFIED. A hash by itself does not prove that an event happened.
~~~~

## How the owner key can be trusted (the design to follow)

The receipt may carry the COSE_Key (it holds the public key), because the key is checked by its hash, not trusted on its own:

1. Take the public key from the COSE_Key.
2. Compute its Blake2b-224 hash. It must equal `approval.owner_key_hash`.
3. `approval.owner_key_hash` must equal the buyer key hash in the on-chain datum (Check 3 reads the datum from the chain). If it does not, the result is REJECTED, unless the receipt carries the exact fallback label, in which case the output must say "approval key not bound to escrow buyer key (fallback)" as a distinct status, not a plain pass.
4. Only then verify the Ed25519 signature over the COSE `Sig_structure`, and check the payload equals the exact approval message `{domain: "seyvixa-approval-v1", action_hash, nonce, expires_at}` built from the receipt fields (canonical JSON, same canonicaliser as the rest of the verifier).
5. Check the address in the COSE_Sign1 protected header has a payment credential equal to `owner_key_hash` (Blueprint 6.5 step 5).

This keeps the rule "never use a key supplied in the evidence" true: the key is only accepted if its hash matches the on-chain datum.

## Assumption that needs Abdul's OK before you change any schema

`schemas/receipt.v0.schema.json` has `approval.signature` (a string) but no place for the COSE_Key. CIP-30 `signData` returns two values: `signature` (the COSE_Sign1) and `key` (the COSE_Key). To verify, the receipt must carry both.

Proposed minimal change: add one field, `approval.key` (COSE_Key as lowercase hex), required, next to `approval.signature` (now the COSE_Sign1 as lowercase hex).
