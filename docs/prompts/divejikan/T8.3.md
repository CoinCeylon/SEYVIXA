## Goal

```

```

## Blueprint excerpts

Copied from `docs/blueprint-v4.4.md`, Section 6.8 (verification steps, result). Section 9 item 12 also applies: verify against pinned keys, never keys supplied inside the evidence.

~~~~markdown
1. Load the public key, recompute its fingerprint and compare it with the trusted fingerprint. Validate the receipt against the schema for its view. Canonicalise the payload and verify the signature.
2. Verify the owner's approval signature over {domain, action_hash, nonce, expires_at}. Confirm that owner_key_hash equals the buyer key hash in the on-chain datum (or report the "approval key not bound to escrow buyer key (fallback)" label). In the full view, also recompute action_hash from approved_action.
3. Lock transaction. Through a chain-data API, confirm that lock_tx_id is confirmed on the expected network, that the output at escrow_utxo_ref sits at script_address with the stated amount, and that its inline datum carries the buyer key hash, supplier key hash, amount, refund deadline and commitment.
4. Recompute the action commitment from action_hash and commitment_salt and compare it with the datum.
5. Settlement.
   - released: confirm release_tx_id is confirmed on the expected network, that one of its inputs is exactly escrow_utxo_ref, that an output pays at least the locked amount to the supplier key hash from the datum, and that the buyer key hash is among its required signers.
   - refunded: the same checks with refund_tx_id, an output paying the buyer key hash, and a validity range that starts after the refund deadline.
   - locked: there is no settlement transaction. Report "locked, not settled" and make no release claim.
6. Check the Midnight verification reference where the toolchain allows independent checking. Otherwise state that this item rests on SEYVIXA's signature.

The result is VERIFIED, REJECTED (any check fails) or UNVERIFIABLE (a chain API could not be reached). UNVERIFIABLE is never reported as VERIFIED. A hash by itself does not prove that an event happened.
~~~~

## Steps

1. Plan mode first. List assumptions, the check order, and the test list.
2. Build the CLI with `--receipt` and `--trusted-fingerprint`. Reject a missing or malformed fingerprint before reading anything.
3. Check 1 first, and stop on failure. Recompute the public-key fingerprint from `keys/receipt-signing-public.json`, compare it with `--trusted-fingerprint`, then check `receipt.kid` against the prefix. Reject any receipt that embeds a public key or a different algorithm.
4. Validate the receipt against `schemas/receipt.v0.schema.json` with `schemas/validate-receipt-v0.mjs` (T8.5). Canonicalise with `packages/shared` (read only) and verify the Ed25519 signature.
5. Checks 2 to 5 as quoted above. Each check returns pass, fail or unverifiable, with a plain message.
6. Output one line: VERIFIED, REJECTED or UNVERIFIABLE, plus the list of checks and their results. No secret or key material in the output.
7. Tests (real behaviour, mocked chain API only):
   - wrong fingerprint stops at check 1
   - a receipt with an embedded public key or an unknown `kid` is rejected
   - a `released` receipt whose release transaction does not spend `escrow_utxo_ref` is rejected
   - a `released` receipt with no output to the supplier is rejected
   - a `released` receipt with the wrong network is rejected
   - an unconfirmed transaction is never VERIFIED
   - a chain API that is down gives UNVERIFIABLE, never VERIFIED
   - a valid simulated receipt gives VERIFIED
   - mutation check: break one check at a time and confirm a test fails

## Acceptance criteria

- `--trusted-fingerprint` wrong stops verification (test).
- A release that does not spend the escrow UTxO is rejected (test).
- UNVERIFIABLE is never reported as VERIFIED (test).
- Every test listed in step 7 passes, and the mutation check is recorded.
