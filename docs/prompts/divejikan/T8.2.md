## Goal

## Blueprint excerpts

Copied from `docs/blueprint-v4.4.md`, Section 6.8 (Trusted key and fingerprint):

~~~~markdown
SEYVIXA signs receipts with one Ed25519 receipt-signing key, generated once before the demo is recorded.

-   The fingerprint is the SHA-256 hash of the raw 32-byte public key, in lowercase hex. The kid is its first 16 characters.
-   The public key is committed in the repository (for example keys/receipt-signing-public.json).
-   The full fingerprint is also published in at least two places that do not depend on that file: the README, and the submission documentation or the demo video or slide.
-   The private key stays on the server and is never committed. Do not regenerate the key after publishing the fingerprint. If it is lost, publish a new fingerprint and re-issue receipts.
~~~~

Blueprint Section 9 item 12 applies: verify against pinned keys, never keys supplied inside the evidence.

## Steps

1. Plan mode first. List assumptions and the exact files.
2. Generate the Ed25519 key pair once with Node's `node:crypto` (no new library). Abdul runs it, not the agent.
3. Write `keys/receipt-signing-public.json` with the public key only: the raw 32-byte key in base64url or hex, algorithm `Ed25519`, and no private field.
4. Compute the fingerprint: SHA-256 of the raw 32-byte public key, lowercase hex, 64 characters. Compute `kid` as its first 16 characters.
5. Put the full fingerprint and `kid` in `README.md`, with the date and a note: "Do not regenerate after publication."
6. Add the placeholder name `RECEIPT_SIGNING_PRIVATE_KEY=REPLACE_ME_...` to `.env.example`. No real value anywhere in the repo.
7. Tests: the fingerprint recomputed from the public file equals the published one; `kid` is the prefix; the public file contains no private field (a test fails if it does).
