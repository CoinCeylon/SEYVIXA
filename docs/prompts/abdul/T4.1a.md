### Blueprint Section 6.4 (Budget Guard)

~~~~markdown
The budget must be shared across agents.

Example:

-   Approved budget: LKR 120,000
-   Agent A requests a reservation of LKR 70,000.
-   Agent B requests a reservation of LKR 65,000 at nearly the same
    time.
-   Only one reservation may succeed if accepting both would exceed the
    budget.

Implement reservations in PostgreSQL using a transaction and row-level
locking or an equivalent serialisable strategy.

Do not implement this as a simple frontend check. Two concurrent
requests can both pass a non-atomic balance check.
~~~~

## Steps

1. Plan mode first. Describe the lock and how two parallel `reserve` calls are serialised.
2. `reserve(procurementId, agentId, amountLkr, idempotencyKey)`: in one Postgres transaction lock the procurement row with `SELECT … FOR UPDATE`, sum reserved and committed amounts, return `BUDGET_EXCEEDED` if the new amount would exceed the budget, else insert a `RESERVED` row. A repeated `idempotencyKey` returns the same reservation.
3. `commit(reservationId)` moves `RESERVED` to `COMMITTED`. `release(reservationId)` moves `RESERVED` to `RELEASED`. While an action is `UNKNOWN` the reservation stays held.
4. Export a stable signature and error shape. Tell Prabhath exactly what an over-budget call returns.
5. Tests: sequential and parallel calls, idempotent repeat, commit and release.
