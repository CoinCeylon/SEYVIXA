### Blueprint Section 8 (Data Model, with the additive note)

~~~~markdown
## 8. Data Model

Use a small relational schema.

  -----------------------------------------------------------------------
  Table                               Key fields
  ----------------------------------- -----------------------------------
  `users`                             `id`, `name`, `role`,
                                      `owner_address`, `payment_pubkey`,
                                      `payment_key_hash`

  `agents`                            `id`, `name`, `status`

  `agent_grants`                      `id`, `agent_id`, `scopes`,
                                      `spend_limit`, `expires_at`,
                                      `revoked_at`

  `procurements`                      `id`, `owner_id`, `description`,
                                      `budget`, `status`

  `supplier_quotes`                   `id`, `procurement_id`,
                                      `supplier_id`, `amount`,
                                      `quote_data`

  `budget_reservations`               `id`, `procurement_id`, `agent_id`,
                                      `amount`, `status`,
                                      `idempotency_key`

  `approvals`                         `id`, `action_hash`, `approver_id`,
                                      `expires_at`, `used_at`, `nonce`,
                                      `signature`

  `policy_events`                     `id`, `agent_id`, `action`,
                                      `decision`, `reason_code`,
                                      `created_at`

  `actions`                           `id`, `procurement_id`,
                                      `owner_id`, `action_type`,
                                      `canonical_payload`,
                                      `action_hash`, `commitment_salt`,
                                      `status`, `ticket_nonce`,
                                      `ticket_expires_at`,
                                      `idempotency_key`,
                                      `external_ref`, `last_error`,
                                      `updated_at`

  `challenges`                        `id`, `purpose`, `owner_id`,
                                      `procurement_id`,
                                      `supplier_id`, `nonce`,
                                      `expires_at`, `used_at`

  `chain_transactions`                `id`, `chain`, `network`,
                                      `kind`, `tx_hash`,
                                      `escrow_utxo_ref`,
                                      `action_commitment`, `status`

  `receipts`                          `id`, `view`, `payload`,
                                      `signature`,
                                      `key_id`,
                                      `created_at`
  -----------------------------------------------------------------------

Every owner-scoped table carries `owner_id`, set from the authenticated
session and never from the request.

State values: `actions.status` is `PENDING_APPROVAL`, `APPROVED`, `EXECUTING`,
`SUCCEEDED`, `FAILED` or `UNKNOWN`; `budget_reservations.status` is `RESERVED`,
`COMMITTED` or `RELEASED`; `challenges.purpose` is `wallet_registration`
or `midnight_proof`. `external_ref` holds the transaction ID or connector
reference.

**Additive note (24 Nov 2026, see DECISIONS.md).** Minimal additions to the schema above, with no new product module: `agents.credential_hash` (hash only, never the token); `agent_grants.owner_id`, `issuer` and `integrity_tag` (HMAC with a server key over the grant fields); a `suppliers` table (`id`, `name`); `actions.reservation_id`, set by evaluate when it binds the reservation; `actions.policy_version`, the value of the `POLICY_VERSION` configuration constant at evaluation time (execute compares it with the current value). `policy_events.procurement_id`, `policy_events.action_id` and `policy_events.resource` (all nullable), and `receipts.procurement_id`, so events and receipts can be found per procurement. `actions.status` also gains `PENDING_APPROVAL`: evaluate sets it when it returns `APPROVAL_REQUIRED`, and a verified approval moves the action to `APPROVED`. An `ALLOW` that needs no approval goes straight to `APPROVED`. A `DENY` creates no action record, only a `policy_events` row. Supplier credential data for Midnight stays outside the main database, as simulated files from the issuer tool under `contracts/midnight/demo-credentials/`.
~~~~

### Team decision D7 (`docs/DECISIONS.md`, not Blueprint text)

~~~~markdown
| D7 | Schema additions (additive note under Blueprint Section 8): `agents.credential_hash` (hash only, never the token); `agent_grants.owner_id`, `issuer`, `integrity_tag` (HMAC with a server key over the grant fields); a `suppliers` table (`id`, `name`); `actions.reservation_id`. Supplier credential data for Midnight stays outside the main database, as simulated files from Afnan's issuer tool under `contracts/midnight/demo-credentials/`. | Blueprint 6.1 requires issuer and integrity protection for grants; agents need credentials; suppliers need a table. |
~~~~

### Team decision D15 (`docs/DECISIONS.md`, not Blueprint text)

~~~~markdown
| D15 | `actions.status` gains `PENDING_APPROVAL`. Evaluate returns `APPROVAL_REQUIRED` and sets `PENDING_APPROVAL`; a verified approval moves the action to `APPROVED`. An `ALLOW` that needs no approval goes straight to `APPROVED`. A `DENY` creates no action record (only a `policy_events` row). | Section 8 had no status for an evaluated action waiting for approval. |
~~~~

### Team decision D16 (`docs/DECISIONS.md`, not Blueprint text)

~~~~markdown
| D16 | Policy version is one configuration constant `POLICY_VERSION`, bumped by hand when policy logic changes. It is stored on the action as `actions.policy_version` (additive column). Execute compares it with the current value; a mismatch gives `POLICY_VERSION_STALE`. Revoked grants are already caught by revalidation. | The Blueprint binds a ticket to a policy version but gave no source for it. |
~~~~

### Team decision D25 (`docs/DECISIONS.md`, not Blueprint text)

~~~~markdown
| D25 | Migrations are plain SQL files in `apps/api/migrations/`, applied by `scripts/migrate.mjs` using the `pg` library (pinned in `docs/VERSIONS.md`). Each file runs in its own transaction; `schema_migrations` is bookkeeping, not a product table. `pnpm migrate` works on Windows and Linux; a second run applies nothing. The Postgres image must be version 13 or newer (`gen_random_uuid()` is built in). `scripts/` is a new top-level folder not listed in guide 4.1. | The Blueprint names no migration tool. |
~~~~

### Team decision D26 (`docs/DECISIONS.md`, not Blueprint text)

~~~~markdown
| D26 | Types and constraints for Section 8. Ids are `uuid` with `gen_random_uuid()`; times are `timestamptz`; LKR amounts are `numeric(14,2)` (simulated); `scopes` is `text[]`; `quote_data` is `jsonb`; `canonical_payload` and `receipts.payload` are `text` (exact bytes); hashes, nonces, salts and signatures are hex `text`. CHECK constraints for `actions.status`, `budget_reservations.status`, `challenges.purpose`, and `budget_reservations.amount > 0`. UNIQUE: `budget_reservations.idempotency_key`, `approvals.nonce`, `challenges.nonce`, `actions.ticket_nonce` (where not null), `actions.idempotency_key` (where not null), `chain_transactions(chain, network, tx_hash)`. No `ON DELETE CASCADE`. Indexes only on `procurement_id` columns. No CHECK on `users.role`, `agents.status` or `procurements.status` (values not listed in Section 8). | Section 8 gives no types or constraints. |
~~~~

### Team decision D27 (`docs/DECISIONS.md`, not Blueprint text)

~~~~markdown
| D27 | Additive columns: `policy_events.procurement_id`, `policy_events.action_id`, `policy_events.resource` (nullable; foreign keys where applicable); `receipts.procurement_id` (foreign key). Added to the Section 8 additive note. T1.5 and T8.1 use them (their cards are not yet in the pack; the guide rows are unchanged). Owner-scoped tables, which carry `owner_id`: `agent_grants`, `procurements`, `actions`, `challenges`. `supplier_quotes` and `budget_reservations` are scoped through `procurement_id` via one shared query helper that joins `procurements` on `owner_id`; T1.6 creates it and T1.6 and T2.1 must use it. `approvals` are scoped through `approver_id`. `chain_transactions` link to a procurement through `actions.external_ref = chain_transactions.tx_hash`; no new column. | Policy events and receipts need to be found per procurement; Section 8 does not say which tables are owner-scoped. |
~~~~
