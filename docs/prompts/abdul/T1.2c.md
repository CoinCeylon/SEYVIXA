### Blueprint Section 6.2 (checks and evaluate)

~~~~markdown
Every protected tool call must be sent to the gateway before execution.

The gateway checks:

1.  Is the agent registered and active?
2.  Does it have a valid permission grant?
3.  Is the requested tool allowed?
4.  Is the requested resource within scope?
5.  Does the action exceed a spending limit?
6.  Is human approval required?
7.  Is the grant still valid at execution time?

The gateway returns one of:

-   `ALLOW`
-   `DENY`
-   `APPROVAL_REQUIRED`

Example denial:

``` json
{
  "decision": "DENY",
  "reason_code": "RESOURCE_OUT_OF_SCOPE",
  "agent_id": "procurement-agent",
  "requested_resource": "payroll.csv",
  "message": "The agent is not authorised to access this resource."
}
```

The gateway must enforce the decision. Returning `DENY` in an API
response is not enough if the agent can still call the connector
directly.

**Evaluate and execute are separate steps.**

-   `POST /api/actions/evaluate` is a preflight with no side effects. For an `ALLOW` it stores an immutable action record (the canonical payload and its SHA-256 action hash, computed server-side) and returns a short-lived, single-use execution ticket bound to the action hash, the caller (an agent, or the owner session for owner-initiated escrow actions) and the policy version.
~~~~

Any addition goes through shared types and this file. | T0.3b needed a fixed list. |
~~~~

### Team decision D16 (`docs/DECISIONS.md`, not Blueprint text)

~~~~markdown
| D16 | Policy version is one configuration constant `POLICY_VERSION`, bumped by hand when policy logic changes. It is stored on the action as `actions.policy_version` (additive column). Execute compares it with the current value; a mismatch gives `POLICY_VERSION_STALE`. Revoked grants are already caught by revalidation. | The Blueprint binds a ticket to a policy version but gave no source for it. |
~~~~

## Steps

1. Plan mode first.
2. Use the existing `actions.ticket_nonce` and `ticket_expires_at` columns. The ticket must be unguessable.
3. Bind the ticket to the action hash, the caller (agent id or owner session) and the policy version.
4. Policy version (decision D16): one configuration constant `POLICY_VERSION`, bumped by hand when policy logic changes. Bind the ticket to the value stored in `actions.policy_version`. Execute (T1.3) compares it with the current value and returns `POLICY_VERSION_STALE` on a mismatch.
5. Write `validateTicket()` that returns `TICKET_INVALID`, `TICKET_EXPIRED` or `TICKET_USED`. Consuming it is T1.3.
6. Tests: a ticket for another action hash or caller is invalid; an expired ticket is expired.
